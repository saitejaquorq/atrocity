<!-- sdlc:auto:start overview -->
atrocity is an AAA video game release tracker generated by the Quorq AI SDLC platform. It is a single repository containing two independently run applications: a Vite + React 19 single-page frontend whose screens were approved against seeded sample data, and a FastAPI backend scaffold that currently exposes only a health check (no architecture had been approved when the backend was generated). The backend uses SQLAlchemy models against a SQLite database by default (swappable via DATABASE_URL), and the frontend's api.ts client is the seam intended for wiring screens to real endpoints later.
<!-- sdlc:auto:end overview -->

<!-- sdlc:auto:start prerequisites -->
- Node.js (for the frontend, Vite 6 / React 19 toolchain)
- Python 3.12 (matches backend/Dockerfile base image)
- pip
- Docker and Docker Compose (optional, for the Postgres 16 service in docker-compose.yml)
<!-- sdlc:auto:end prerequisites -->

<!-- sdlc:auto:start setup -->
1. Clone the repository
2. cd backend && pip install -r requirements.txt
3. (optional) Start a local Postgres via `docker compose up db` if you want to point DATABASE_URL at Postgres instead of the SQLite default
4. cd backend && uvicorn app.main:app --reload  # starts the API on http://localhost:8000
5. cd frontend && npm install
6. cd frontend && npm run dev  # starts the SPA on the Vite dev server (default http://localhost:5173)
<!-- sdlc:auto:end setup -->

<!-- sdlc:auto:start conventions -->
- Backend routers are organized one-per-architecture-component under app/routers/, with one route per declared API endpoint.
- Unimplemented backend routes return a typed StubResponse placeholder (status/detail fields) rather than erroring, keeping the service startable with a complete OpenAPI doc.
- SQLAlchemy models inherit from the shared Base in app/database.py; models.py must be imported before create_all runs so tables register (done in main.py's lifespan).
- Request-scoped DB access goes through the get_db dependency, which yields a session and always closes it.
- Backend DB URL defaults to local SQLite (DATABASE_URL env var overrides it, e.g. for Postgres); CORS allowed origins default to the local Vite dev server and are overridden via ALLOWED_ORIGINS (comma-separated).
- Frontend screens live under src/screens/ (one module per approved screen) and currently render seeded sample data rather than calling the API.
- Frontend API integration is centralized in src/lib/api.ts (apiFetch helper, API_BASE_URL, bearer-token session handling) as the intended seam for wiring screens to the backend.
- Frontend component tests sit beside the components they test; Playwright e2e specs live separately under e2e/.
<!-- sdlc:auto:end conventions -->

<!-- sdlc:auto:start troubleshooting -->
| Problem | Solution |
|---|---|
| Frontend dev server calls to the API fail with a CORS error in the browser. | Set the backend's ALLOWED_ORIGINS env var to include the frontend's origin (defaults to http://localhost:5173 / http://127.0.0.1:5173 if unset). |
| `npm run build` succeeds but the app later fails type checks or deployment. | Run `npm run typecheck` (tsc --noEmit) locally and fix errors before shipping; `build` does not typecheck. |
| Backend fails to start or endpoints 500 on first run. | The lifespan handler creates tables from app/models.py via create_all on startup; ensure DATABASE_URL (default sqlite:///./app.db) points at a reachable database, and that backend/requirements.txt dependencies are installed. |
| `pytest` run from backend/ can't import `app`. | Run pytest from the backend/ directory so pytest.ini's `pythonpath = .` applies, or run `cd backend && pytest`. |
| Playwright e2e run fails to boot the backend. | test:e2e expects a Python venv at backend/.venv with dependencies installed (`.venv/bin/python -m uvicorn ...`); create that venv and install backend/requirements.txt before running `npm run test:e2e`. |
| `docker compose up db` starts Postgres but the backend still uses SQLite. | The backend only switches databases when DATABASE_URL is set to point at the compose Postgres service; export DATABASE_URL accordingly before starting uvicorn. |
<!-- sdlc:auto:end troubleshooting -->
